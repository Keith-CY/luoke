# 推理和权重归主控：体系里没有脱离主控的 LLM 运行实例

2026-10-16 johnz 提议；2026-10-19 主人看过审阅后定：不设例外，垂类模型也经主控跑。一步到位，不设过渡方案。

## 决定

1. **本机的模型推理和权重都归主控，没有例外。** 主人原话："我们体系里不应该有脱离主控的 LLM 运行实例"（顶层 ADR 0014 的修订也引了这句）。
   - 这是 ADR 0014"本机所有模型的加载……由主控管"的落实，不是新原则。
   - 权重归主控也是现有做法：下载、版本、校验都走主控的分发（配方、发布清单，见 luoke-core DESIGN §3、§7）。各工具不自带模型，也不自己加载模型。
2. **垂类模型也经主控跑。** 只给某一个工具用的专门模型（不是底座），同样做成主控的任务：工具按任务要结果，不点名模型；权重、版本、评测和别的模型一样由主控管。现在有两个：digup 的嵌入模型、隐私模型（PII-Tracer）（隐私模型是否接入待定），见下面「垂类模型怎么接主控」。
3. **对延迟敏感的，走主控的优先通道。** 每次请求都在关键链路上的垂类模型，不靠"留在工具里自己跑"解决延迟，而是走主控的优先通道，和嵌入一起，由 luoke-core 设计。

## 为什么

- 显存、功耗、排队只能有一处管（ADR 0014）。两份权重、两套内存判断会撞车：ADR 0014 修订里，主人自己的 oMLX 和主控就是这样撞上的。
- 一步到位：johnz 提出一步到位，主人审阅时认可了原则部分。"工具自带一份、主控也有一份"要维护两套下载和版本，反而更乱。

## 垂类模型怎么接主控

先看能不能复用主控现有的任务类型（生成、打分、嵌入）；都不合适，再加新的任务类型，只加不改（luoke-core V1 §2，对外约定 1）。

每个垂类模型的接入方写清两件，luoke-core 按这个定接口和优先通道的容量：
- 要什么接口：嵌入、打分，还是新的任务类型；
- 延迟要求：每次多大的输入，最慢能等多久。

### digup 的嵌入（已实现，luoke-core#5）

- **接口**：嵌入，`POST /tasks/<任务>/v1/embed`。
  - 请求是调用方加好前缀的整段文字。
  - 答复是满 768 维、L2 归一化的向量，带 `vector_space`：调用方凭它判断已有的索引能不能接着用。
  - 完整格式见 luoke-core V1 §2。
- **延迟**：
  - 搜索时的单条查询（≤ 64 字）端到端 p90 在 100 ms 以内（M1）。这是起点，等实测再定；实验室在 M3 Pro 上实测 p90 11.3 ms。
  - 建索引走后台请求。
- **评测**：对 digup 的参考向量集余弦 ≥ 0.999 是及格线。参考集覆盖文字、截图、照片、视频帧和声音；文字 5 条已用真模型核对通过，最低 0.99977。
- **现状**：
  - beta1 带代码，但配方不分配到任何档，各档答 `unsupported`。
  - 文字部分，主控自带了 mlx-vlm 里那个模型的代码（johnz 10-16 批；主人的 luoke-core 会话审 luoke-core#5 时核过合规），引擎包不动。
  - 图片和声音要等主控换上带新 mlx-vlm 的引擎包；johnz 提议放在 beta1 之后，先在实验室验 rc1。digup 等多模态能用再发布（johnz 批的 A）。

### 隐私模型 PII-Tracer（是否接入待定，不排进 beta1）

**是否接入待定，不排进 beta1。** 主人说隐私模型"最终可能不用在我们体系里"。下面是接入方 10-19 交来的接口和延迟记录，留作备用；决定接入以后，再由 luoke-core 设计。

- **模型**：`perplexity-ai/PII-Tracer` @ `d25c16f`（MIT）。编码器，骨干和 Qwen3 0.6B 同尺寸，双向注意力，bf16 权重 1.19 GB。两个输出：
  - 每个 token 一组标签分数（不是个人信息，加 9 类个人信息各自的 BIOES），经模型自带的受约束 Viterbi 解码成片段；
  - 每段一个 0–1 的敏感度。
- **接口**：要一个**新的任务类型**，暂叫「标签」（tag，名字由 luoke-core 定）。嵌入只给每段一个向量，打分只给候选的概率，都给不出每个 token 的标签和位置。接入方的建议：
  - `POST /tasks/<任务>/v1/tag`，请求 `{"texts": [...]}`，一次请求的所有段一起送。
  - 答复：每段一组片段（`start`、`end`、`label`、`score`，`start` 和 `end` 是原文字符偏移），每段一个 `sensitivity`，再加 `model`、`ms`。
  - 分词、偏移映射、Viterbi 解码都在主控里做，调用方不碰 token。
  - 超过窗口（4,096 token）的段由主控开窗、重叠一半再合并；也可以答 `input_too_long`，由调用方自己切。
  - 标签集和模型版本算进 `tasks_version`（像嵌入的 `vector_space`）：同一版本同样的输入，输出必须一样。
  - 一次调用里的所有段放进一次批量前向。现在每次前向的固定开销约 45 ms，一次调用要 5–11 次前向。
- **输入多大**：接入方在 M3 Pro 上用合成数据和 luoke-mail 的示例收件箱实测，现在逐段前向、还没批量。

  | 一次调用 | token（典型 / 最大） | 段数 | 最长一段 | 模型时间 p50 / p90 / 最大 |
  |---|---|---|---|---|
  | 分析一封 | 725 / 759 | 8–11 | 433 | 362 / 386 / 422 ms |
  | 起草一封 | 263 / 297 | 5–8 | 125 | 171 / 198 / 236 ms |
  | 清理一批（25 封） | 1,304 / 1,428 | 7 | 1,066 | 530 / 587 / 658 ms |
  | 退订一批（10 个） | 525 / 629 | 5 | 413 | 255 / 277 / 327 ms |

  - 大部分 token 是调用方自己的提示词，最长取决于调用方任务的字符上限。人造的单个长段（10,388 token，开 3 个窗口）要 4.7 s。
- **多久调一次**：
  - 只在用户等着结果的请求上调，后台请求不调。用户每点一次就调一次。
  - 平时很少，但要按"用户连点清理"的突发定容量：每批间隔几秒到十几秒，每批约 1.3k token。
- **最慢能等多久**：典型 ≤ 0.5 s，最慢 2 s。超过 5 s 或者主控没答上来，调用方当作失败处理。
- **延迟的解法**：
  - 走主控的优先通道，和嵌入一起，由 luoke-core 设计；luoke-core 按上面的数定通道容量。
  - 冷启动加载要约 5 s，所以不能排在后台生成后面：要像打分那样常驻、走直连路径，或者在调用方需要的期间用预热留住。
- **还要 luoke-core 评估的**：
  - 运行时：现在跑在 PyTorch 上，要 transformers ≥ 5.2 才能跑双向 Qwen3。搬进主控，是把它和这套 Viterbi 解码移植到 MLX，还是起一个 torch 工作进程，由 luoke-core 定。
  - 内存：常驻约 1.2 GB（权重加激活），16 GB 档要算进预算；只在调用方需要的期间常驻。
- 权重、版本、评测和别的模型一样由主控管，调用方不再从 Hugging Face 缓存读。

## Considered Options

- **各工具自带模型 / 模型放各自的仓库**：否决。显存只能一处管，下载和版本会变成多套；digup 原来自带 llama.cpp + EmbeddingGemma 2 就是这样。
- **先过渡、再统一**（工具先自带，逐步挪到主控）：否决。johnz 提出一步到位，主人审阅时认可了原则部分。
- **对延迟敏感的垂类模型留在用它的工具里自己跑**：否决。主人 10-19 定没有例外；延迟用主控的优先通道解决。

## Consequences

- **luoke-core**：
  - 现在只做嵌入（luoke-core#5）和优先通道。
  - 隐私模型等决定接入以后再做：新加「标签」任务类型（名字由 luoke-core 定）、定运行时（MLX 移植或 torch 工作进程）、任务和权重进配方，优先通道的容量那时再把它算进去。
- **digup**：已改调主控的 `/v1/embed`，去掉自带的 llama.cpp 和模型（digup 分支 `claude/digup-core-embed`）。发布跟着嵌入真正能用（含多模态）走。
- **隐私模型的接入方**：决定接入以后：接口和延迟要求已交给 luoke-core（10-19），还要写进自己的注册页；权重改从主控的分发拿。
- **ARCHITECTURE §2「模型推理」一行**：补一句"模型权重也归主控，下载、版本、校验统一走主控的分发，各工具不自带模型；体系里没有脱离主控的 LLM 运行实例"。
- **许可证**：嵌入这条链没有 GPL：DigUp、llama.cpp、mlx-vlm 都是 MIT，EmbeddingGemma 2 的权重是 Apache-2.0。

## 修订（2026-10-20）

- **digup 不登记，嵌入由 luoke-search 接手**：主人 10-20 定 digup 不作为螺壳的项目登记，相关需求重新做成"螺壳深度搜索"（luoke-search，工具层，入口在 agent，注册页 `projects/luoke-search.md`）。上面「digup 的嵌入」一节的接口、评测和多模态安排原样由 luoke-search 接手，主控的任务名由 `digup.embed` 改为 `luoke-search.embed`（接口不变）。参考向量集从 digup 原样拷到 luoke-search。

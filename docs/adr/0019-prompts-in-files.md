# 提示词放成文件：每个配件一个 `prompts/`，顶层一页总览

2026-10-23 早会主人定为高优先级的重构目标："产品中所有的提示词都应该放在一个固定的地方，方便人工精修"。luoke-top 盘点后写了提案，主人同日照推荐定下，放在 beta1 之后的下一版推进。

## 决定

1. **每个用到模型的配件，提示词放在仓库根目录的 `prompts/` 里，格式统一**：每个任务一组纯文本文件：
   - `<任务>.system.txt`：固定说明；
   - `<任务>.user.txt`：每次输入的措辞和顺序；
   - `<任务>.retry.txt`：答错后补的纠正话；
   - `<任务>.schema.json`：输出格式。

   本仓库共用的句子放在 `_shared.txt`。代码只负责读文件、取字段、截短、填占位符、发请求和解析，不再在代码里写提示词。
   - 用 `.txt` 和 `.json`，不用 `.md`：出版判断配件有没有改动时排除了 `*.md` 和 `docs/`。
   - 占位符严格核对：要填的没填、填了的不在文件里，加载时就报错。
   - 枚举（类别、动作、话题列表）只写在 `schema.json` 里，提示词用占位符引用，不再手抄。
   - 配方里的开关（例如 `sender_verdict`）在文件里写成可选段，开关逻辑留在代码。
2. **顶层一页总览**：atlas 的「任务与提示词」页改为从各配件的 `prompts/` 生成。内容包括全文、占位符说明、用在哪几档、评测集和最近的分数，放在公开站上。精修的人从这一页找到文件，在对应仓库提 PR 只改 `prompts/`，三档重评分数不降才合并。
3. **出版证据记下提示词指纹**：每个任务的评测证据加 `prompt_sha256`（这个任务所有 prompts 文件的哈希），版本对照标出哪些任务的提示词变了。配件有改动就重评，这一点不变。
4. **补评测集**：没有评测集的任务（邮件助手的起草回复、订阅阅读、精选挑选）各补一个，精修要有分数兜底。
5. **新配件一开始就照这个格式写**（写进 `docs/new-component.md`）。

## 为什么

- 提示词散在代码常量和 f-string 里，和解析逻辑混在一起，要人工精修得先读懂代码；枚举两处手抄，改漏了不报错。
- 放在各配件自己的仓库，而不是一个统一仓库：提示词和读它的代码、它的评测集同进同出，出版的改动判断和"每个配件版本都要验证"（luoke-core ADR 0008）照常生效，负责人管得到自己的提示词；这也守住了"提示词在配件里，数值在配方里"（luoke-core ADR 0005）。"一个地方找"由顶层生成的总览页来给。

## 不选的做法

- **全部提示词放进一个独立仓库**：配件和提示词分在两处，改一处要两边对齐，出版的改动判断看不到别的仓库，负责人也管不到自己的提示词。
- **提示词放进主控、由主控渲染**：luoke-core ADR 0005 已否决，主控会被迫懂每个配件的业务。

## 怎么做

1. **邮件助手的 9 个任务、记忆的 2 个、体检的 2 个**照格式搬出来。搬家那一版的要求：所有评测题拼出来的消息逐字节不变（搬前存快照、搬后比对），照常三档重评。记忆片段的标题（`LABELS`）也放进 luoke-mem 的 `prompts/`，agent、输入法里的副本跟着更新。
2. **luoke-top** 生成 atlas 总览页，**luoke-core** 在证据里记 `prompt_sha256`。
3. **luoke-mail** 补三个评测集，**luoke-core** 放进配方。

提案和盘点：luoke-ops `docs/prompts-refactor.md`。

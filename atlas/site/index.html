螺壳系统文档

螺壳（Luoke）是螺壳实验室（Luoke Labs）开发的一组本机 AI 工具：所有模型推理和数据都在用户自己的 Mac 上。本文档描述系统的结构、各组件的职责与接口、数据如何流动，以及运行和发布方式。

核心原则

  • 本机就是边界：数据不离开用户自己的设备；在本机内部，各组件可以读取完成工作所需的任何数据。
  • 模型只经主控：所有推理通过主控的任务接口进行，组件不自行加载模型。
  • 只有记忆形成结论：工具记录发生了什么，记忆据此形成带依据、分三档把握程度的理解。
  • 先做、事后复查：能撤回的处理在用户确认一次习惯后自动执行并给出提示；不可逆或对外的操作始终由用户点按。
  • 凭证不进记忆：密码、验证码、密钥、令牌、完整卡号和证件号在写入时遮去。

核心概念

配件

由主控安装和管理的一个签名 .app，例如邮件助手、输入法、agent、深度搜索（规划中）。每个配件在 luoke-accessory.json 中声明自己的身份、需要的任务、空闲任务、数据目录和给 agent 的能力。Python 配件自带固定版本的 Python。记忆没有独立的 .app，它打包在主控里。

任务

配件向主控请求推理的单位，名字形如 luoke-mail.triage。配件只说要哪个任务，不指定模型；主控按配方和机器的硬件档决定用哪个模型、参数是多少。任务分四种：

kind做什么例子
generate生成文字（流式，约束为 JSON）邮件分拣、记忆归纳
score给候选打分输入法重排
predict续写输入法联想
embed向量深度搜索

提示词、输出格式和业务判断写在调用任务的配件里；主控只提供通用的推理能力。

硬件档

按内存把机器分为 16、32、128 三档，每档有自己的底座模型、内存上限和底座是否常驻。每个任务在哪一档开启，由评测决定：关着的任务连续 3 遍全部通过才开启（当天评一遍，另两遍在发布后补跑，下一版生效），开着的一遍不过即关闭。

请求等级

主控按三个等级调度：打字（输入法打分和联想，最优先）、用户在等（用户正在等结果的请求）、后台（可以等待的工作）。后台工作只在机器空闲、接通电源、未过热、内存充足时运行，用户一回来就让路。

空闲任务

配件登记的"空闲时运行"的命令，例如记忆的归纳、邮件助手判断旧邮件。主控只决定何时启动（安静时刻、满足最短间隔），不关心它做什么；用户回来时让它收尾。

记录

工具写入记忆的"发生了什么"：谁（用户、第三方、规则自动执行）、做了什么、什么时候真实发生，可附原文。记录是理解的依据。

理解与把握程度

记忆从记录归纳出的关于用户的认识：事实、关注的话题、不感兴趣、处理习惯、常用说法、精选口味。每条理解引用它的依据，并有三档把握程度：

档含义谁能用
猜测推出来但证据不足不使用，只在记忆界面中显示
比较确定依据足够各工具可以使用
确定用户说过或确认过各工具可以使用，可据此自动执行

一条推断能到哪一档，取决于依据的类型和数量（见记忆 · 定档规则）。会变的理解太久没有新依据会变成"以前的事"。

提问与建议

记忆在空闲时整理理解，产出两类请求：提问（只问用户才能定、答了有用的猜测）和建议（如"以后这类邮件都自动归档？"）。它们由 agent 或相关工具的页面展示，用户的回答交回记忆定档。

处理习惯与自动执行

用户对某个发件人某类邮件反复做同样的处理，记忆形成一条处理习惯并建议自动执行；用户同意后，邮件助手在同步时照做。只有能撤回的动作（归档、标已读、加标签）会自动执行，每次都可在"今日处理"中撤销，撤销一次即视为反证。

能力

工具在清单中向 agent 声明的可报事项和可执行动作，经工具协议（MCP 子集）调用。会改动数据的调用只在用户点按卡片时发出。

提问和建议

  1. 记忆的反刍在每次归纳任务的开头和结尾运行，生成提问（每天 ≤ 2）和建议（每天 ≤ 3），写入 asks。
  2. agent 每 300 秒读取一次，在窗口、通知或简报中展示；与邮件有关的建议也在邮件助手的记忆页中展示。
  3. 用户的回答经 Memory.reply 交回，记忆据此定档。

外部工具

高级用户可开启主控的本机端点，让 pi 等工具通过 OpenAI 兼容接口使用本机模型，包括用户自己登记的模型。这些请求与配件请求一起由主控调度，按"用户在等"处理。

主控

本机所有模型推理的唯一入口，也是螺壳的安装器。它按配方为每个硬件档选择模型，调度各配件的请求和空闲任务，监管推理引擎和专用模型进程，并负责下载、升级和卸载。

生命周期

启动

  1. 本体判断是否以安装器身份运行（文件名不是 螺壳主控.app、位于 /Volumes/ 或被系统隔离），是则进入安装流程。
  2. 首次运行未完成时显示首次运行向导；否则启动主控进程，有升级标记时显示升级页，然后拉起常驻配件；清理上次经"检查更新"升级时挂载的安装包。
  3. 主控先绑定 socket 并应答（启动期间除 /tasks、/status、/downloads 外答 busy），再启动引擎：清理上次留下的孤儿进程、等待底座出现、做冒烟检查。
  4. 启动采样线程，进入运行状态；设置中开启了端点则开启端点。

运行

采样线程每 5 秒检查引擎是否崩溃，刷新电源、温度和内存压力，按需打断后台工作、卸载闲置底座、跑探针、每 60 秒重扫配件清单、调度空闲任务，并写入 state.json。本体每 3 秒轮询一次 /status。空闲超过 10 分钟的专用模型工作进程停掉；内存压力 critical 时全部停掉，30 秒内不起。

退出

本体发 SIGTERM，等待 40 秒。主控依次停止端点、空闲任务（SIGTERM，15 秒后 SIGKILL）、工作进程、引擎，最后删除自己绑定的 socket。

调度

请求等级

等级来源待遇
打字打分、联想（输入法）立即处理；记为交互；16 GB 档会立即卸载底座让出内存
用户在等生成请求带 X-Luoke-Priority: user-waiting；端点请求优先；正在运行的后台工作若预计剩余超过 11 秒则被打断（返回 interrupted）
后台X-Luoke-Priority: background；空闲任务需通过后台接纳

交互中指最近 60 秒内有过用户在等的请求或新的预热；安静时刻指距最近一次此类事件满 5 分钟。

功耗档：全速、均衡、安静；每项后台工作结束后按占用时长的 0、1、3 倍歇息。专用模型通道（嵌入）每个任务有独立通道和间歇，不占用引擎的后台名额；用户在等的嵌入查询插在后台批（每 8 条）之间。

内存

  • 模型能否加载要过两道检查：大小不超过引擎上限 (guard_gb − 2) × 0.95；且不超过 Metal 可用上限减去当前 wired 内存（按物理内存的 74%–84% 估算）。端点的用户模型独占引擎时，上限改为 内存 − 8%（3–8 GB）− 常驻专用模型 − 1 GB，换回底座时还原。
  • 起专用模型工作进程前先算剩余内存（Metal 上限 − wired + 已加载的底座），装不下它的 wired_gb 就不起，答 not_ready（retry_after 30）。
  • 引擎上限随正在运行的工作进程动态调整。
  • 引擎同时只有一个"当前模型"；端点登记的小模型放得下时与底座同时加载，放不下则独占（先卸掉其他模型）。
  • 底座闲置超过本档 idle_unload_secs 后卸载；有后台工作或有效的预热租约时不卸。

空闲任务

同一时间只运行一个。启动条件：主控空闲、处于安静时刻、后台未暂停（清单可声明允许电池）、距上次启动满 min_interval_minutes（上次被收尾时缩短为 10 分钟）。用户回来、超时、后台暂停或卸载配件时收尾。

配方和档位

  • 配方（recipe.json）定义硬件档（内存范围、引擎上限、底座是否常驻）、模型（目录、类型、常驻内存）、每档的模型分配、引擎版本、每个任务的参数、允许接入的配件版本和评测证据。
  • 选档：取第一个满足 min_gb ≤ 内存 < max_gb 的档；用户可在设置中选择更低的档（如 128 档的"省空间"）。
  • 任务开关：每个任务在哪一档开启由出版流程的支持台账决定：未开启的档须连续 3 遍评测全部通过才开启，开启的档一遍不过即关闭。
  • 冒烟检查：引擎启动后测一次实际的预填和生成速度，后台估时使用实测值。
  • 探针：打分、联想工作进程就绪后测 p90 延迟，超过配方 latency_ms 时把任务标为较慢。

下载、安装、升级、卸载

  • 下载：依据发布清单（每项有文件列表、大小、sha256、多个镜像地址）。多地址时先测速排序；每个地址重试 3 次，403、404、410 直接换地址；支持续传；sha256 对上才落位。本机已有同名模型（~/.omlx/models、Hugging Face 缓存、LM Studio）时逐文件核对后 APFS 克隆，不重复下载。
  • 配件安装校验：codesign --verify --deep --strict、Team ID、bundle id 与清单一致、公证票据有效。
  • 首次运行：步骤条五步：这台 Mac（预检：档位、磁盘、系统版本、照实说明体验）→ 选应用 → 确认下载 → 下载安装（含本机试跑）→ 完成；升级时三步：要更新的 → 更新 → 完成。完成页：注册登录项；输入法的 --status 答 not_registered 时调一次它的 --register，每秒检查是否已添加，添加后改提示；列出每个应用的通知权限（经启动器的 --notify-status）：已允许 / 还没问过（按钮发一条测试通知，让系统询问）/ 已关闭（按钮打开该应用的通知设置），未全部允许时每 2 秒刷新。
  • 升级：新安装器的 built_at 更新时，旧主控移入 previous.noindex，新主控显示升级页，按新清单更新引擎、模型和比清单旧的应用（不降级，不重装用户回滚掉的版本）；可回到上一版。
  • 检查更新：菜单「检查更新…」按本机主控的渠道（内部版 internal-*、beta beta*）查 luokelabs/luoke-releases，built_at 更新才算；升级时下载主控 DMG，核大小、sha256、公证票据、签名和 Team ID，再打开它走原地升级。本机版、开发版不查。默认每天自动检查一次，只在菜单显示「有更新：<版本>…」，不自动安装。
  • 配件回滚：菜单「配件回到上一版…」把配件与 previous.noindex 里的旧版对调（先核签名、Team ID、bundle id、公证，按路径结束进程，不动输入源；再点一次换回）。主控把每个被本版配方认可的配件版本及其通过的任务记入 verified-history.json（每配件 3 个版本）；换回的版本只能用记录中的任务，无记录的不能换回。
  • 卸载：输入法先停用输入源；结束进程；删除 .app 时连同 previous.noindex 里的旧版；可选"一起从记忆里忘掉"和"删除数据"。只删除配件清单 data 中声明且符合配件自身标识的路径；不删除 mem.db。"卸载全部"删除环境目录、登录项和主控本身。

三档把握程度

由状态推出，不单独存储：

档条件

  • 名字只有品牌或来源名（如"Zillow""X 相关动态"）的话题不会成为兴趣。
  • 第三方来信推出的事实：同一来源 ≥ 6 封、跨 ≥ 3 个月、打开 ≥ 2 封、最近 6 个月内仍有来信时直接生效。
  • 健康、法律、宗教政治相关的推断必须由用户确认。

  • 以前的事：会变的理解（包括用户确认过的）最新依据超过 730 天，标为 past，不再使用也不再提问，相关的未答问题撤回；姓名、学校、家人等不会变的不受影响。用户说"现在还是"即恢复为确定；同一类被这样唤回 ≥ 2 次后，这一类的期限加倍为 1460 天。
  • 以前的事再次出现（工具又提出同一条）：只因太久而变成以前的事的，按原样回来——用户确认过的回到确定，否则为猜测、按新依据定档；用户自己说过"以前是，现在不是"的回到猜测，保留表态时间，新依据不能让它自行生效，只能再问用户。
  • 邮件推出的兴趣：关于用户的、由邮件记录撑起的兴趣最多 8 条生效；重新定档时按依据条数保留前 8 条，其余回到猜测。
  • 取代与合并：同类同话题的新理解生效时，取代用户未表态的旧推断（"其他"话题除外）；说法相近的话题合并为一条。

反刍

不使用模型，每次归纳任务开头和结尾各执行一次；结果计数写入 learning 表 rumination.last。

  • 降档：打字归纳出的兴趣和常用说法，最新依据超过 90 天且用户未表态，回到猜测。
  • 处理习惯：同一（邮箱, 发件人, 邮件类别, 动作）出现 ≥ 2 次形成一条习惯；来源是 mail-override 的新建议和 mail-acted 的动作，只认 ACTION_NAMES 里的动作（archive、read、trash、spam、flag、keep、label、filter）。来自改建议的按定档规则判定，仅来自亲手处理的为猜测。用户撤销一次自动执行即回到猜测。
  • 想问的：只问兴趣和处理习惯里依据无法自行撑到比较确定、180 天内有依据、不敏感的猜测，按最新依据和依据条数排序；每天最多 2 个，14 天过期；不再值得问的撤回。
  • 建议：每天最多 3 条。"以后都这样？"（有发件人和类别、动作可自动执行的处理习惯，用户点"好"即成为确定并可自动执行）；"退订？"（30 天内用户亲手整批清掉同一发件人 ≥ 2 次）。
  • 去重：同一件事已有未答的问题时不再生成；"以后再说"或过期未答 7 天后、已答或"不用"60 天后才可能再问；"别再提"永不再问。

邮件助手

用本机模型整理整个邮箱：逐封分拣近期邮件，清理旧邮件，体检订阅并挑选精选，起草回复放入草稿箱。可撤回的处理会自动执行，并在"今日处理"页集中复查。

职责

  • 为每封邮件给出建议（回复、加入日程、待跟进、归档、移到垃圾箱），附类别、优先级、摘要、截止日期、日程字段、回复要点和可疑标记。
  • 执行用户的操作并保留撤销步骤：归档、移到垃圾箱、移到垃圾邮件、加星标、标已读、加标签、写草稿、生成日历文件、退订。
  • 不发信，不永久删除：删除即移到垃圾箱，回复只存入草稿箱。
  • 把用户的操作写成记忆记录；关于用户的结论由记忆形成。

同步与分拣

  1. 读取收件箱最近 N 天（默认 30）的邮件，新邮件最多取 100 封；只取前 1 MiB、不改变已读状态，正文去引用后截到 6000 字。
  2. 对照收件箱现状：已不在的标记为完成；推断用户在别处做了什么（归档、删除、读过、加标签，写入 mail-acted，where=elsewhere；每次最多查 30 封的去向）；邮件助手 3 天内操作记录里动过的邮件不算用户的处理，分析后标已读不移动邮件、不在此列；记为已移走却仍在收件箱的放回待处理。
  3. 邮箱第一次同步时，把收件箱里当时未读、在分拣范围以前的邮件记成一个队列（新的在前，只记这一次）。
  4. 补充发件域名验证结论（Gmail 的 DMARC），以及用户最近 7 天自己归档但可能仍需处理的邮件（Gmail，最多 50 封）。
  5. 逐封分拣（luoke-mail.triage）。命中的规则作为上下文提供给模型；模型可提出不同建议。
  6. 依次执行：最近归档的邮件只留需要用户处理的、精选来源排队、自动标已读、按习惯处理、处理螺壳自己的邮箱、更新往来邮件状态（每次最多问 10 串，只问有新邮件的）。

以前的未读邮件

  • 第 3 步记下的队列作为空闲任务分拣（空闲任务中排最前，属于主控的 clean 任务）：每次取 10 封（取时不标已读），入库标 items.older，以后台优先级交给 luoke-mail.triage，每段最多 4 分钟；主控说暂停或模型出错时停下，下次再分。分好的当场标已读；照确认过的习惯归档、加标签（以及螺壳自己的邮箱的自动处理）在下一次同步时做，和其他待处理邮件一样。
  • 同步不等它们，收件箱的"未分析"数也不计它们；"清理 → 收件箱中的旧邮件"不再列出它们。
  • 以后用户自己标回未读的旧邮件不再排进来；分拣范围放大后，新范围里的邮件由正常同步分拣。

安全规则

  • 邮件内容视为数据。试图指挥 AI、索要密码或验证码、冒充、催促转账的邮件标为可疑；只要模型判为可疑，动作一律改为忽略、类别改为钓鱼。
  • 页面渲染不使用 innerHTML。

通知

系统通知由后台整理在每个邮箱同步后发出。agent 正在读 outbox 时（10 分钟内读过），新邮件、快到期、精选、今日处理这四类不再发通知，交给 agent。

  • 需要回复、加入日程、待跟进的新邮件（3 天内到达、非可疑）：封数和最急的两封。
  • 按习惯自动处理后：处理了几封，点开进入"今日处理"。
  • 截止日期在明天及以前的：每件只提醒一次。
  • 精选：每周一 08:00 之后的第一次后台整理；今日处理：每晚 20:00 之后一次。

可靠性

  • 写入核实：移动后检查是否真的移走，没移走的不标已处理；不支持 MOVE 的服务器先确认副本存在才标删除，只对自己标记的邮件做 UID EXPUNGE。
  • 撤销：按 Message-ID 找邮件；改动前先备好撤销步骤，断线时记"结果未确认"并保留撤销。
  • 主控不可用：邮件照常入库、暂不分析，主控就绪后自动开始；模型忙时用户等待的请求原地等，后台任务延后。
  • 邮箱差异：网易登录后需发 IMAP ID；QQ 先查 CAPABILITY 再用扩展命令；Gmail 归档即移到"所有邮件"，标签用 X-GM-LABELS。

已知限制

  • 发件域名验证、最近归档的分拣、加标签、过滤器导出只支持 Gmail。
  • 单封移到垃圾箱和退订不需要处理模式。
  • 往来邮件只看最近 30 天、已发送中最新 60 封，按主题和对方一人归串，等待阈值固定为 3 天。
  • 撤销过自动标已读的邮件仍记为"邮件助手标的已读"，用户之后自己打开它也不计入订阅的打开数。

结构

部分实现职责
壳Swift：LuokeShell（平台无关的状态机和引擎宿主）+ LuokeIME（InputMethodKit 外壳）；另有共用状态机的命令行版按键、组字、候选窗、上屏、沙盒、转问

进程模型

  • 壳由系统拉起（菜单栏不显示）。每个输入框一个 Session；全进程一个 EngineManager，主线程每秒轮询配置和引擎状态。只运行一份：父进程不是 launchd 时直接退出；用 $TMPDIR/ai.luoke.inputmethod.Luoke.lock 文件锁占位（最多等 3 秒），已有一份时退出。
  • 引擎以 posix_spawn 在独立进程组中启动，命令为 /usr/bin/sandbox-exec -p <模板> …，工作目录是引擎文件夹。run[0] 为 luoke-python 时使用主控 .app 内的 Python。自带引擎用固定 PATH；第三方引擎第一次启动时才解析登录 shell 的 PATH（最多 3 秒）。
  • 通信：标准输入输出上每行一个 JSON，第一条必定是 hello；写入走每个引擎自己的串行队列。
  • 停止：关闭 stdin，1 秒后对整个进程组 SIGKILL。
  • 崩溃与卡死：一次询问 1 秒没有答复视为卡死并杀掉；60 秒内崩溃 3 次则停用该引擎。
  • 退出：收到 SIGTERM、SIGINT、SIGHUP 或正常结束时，结束系统日志订阅，并向主控发 POST /accessory/exiting（1 秒超时）。
  • 重启条件：设置文件变化、用户引擎目录变化、非自带引擎的文件变化、options.json 变化、主控 Python 被替换（每 10 秒检查）。

候选流程

  1. 按键经 MacKeys.translate 翻译，进入会话；空闲时按下输入键会读取前文（安全输入时不读）。
  2. 壳向打字引擎发 query；只采用最新一次询问的答复，50 ms 内收到的最后一份直接显示。
  3. 打字引擎先给快答复（改选过的词、苹果候选、RIME 补充），能重排时标 more；再经壳把 score 转给个人化组件，个人化组件转主控 luoke-ime.rerank，最多等 0.7 秒。
  4. 逐词重排：模型得分须比苹果整句首选高出阈值（自然对数 3）才替换；换掉首选时补发答复，界面让新首选淡入。
  5. 空格、数字、标点等收尾键在还没有任何答复时先等第一份答复，最多 1 秒（判定卡死）；卡死则按原始字母上屏，数字原样交给应用。之后最多再为补发等 150 ms。回车、Esc 不等。上屏后，空格或数字选中的会接着请求联想。

联想

  • 在空格或数字选词、标点、快捷键引擎上屏后触发；需全局和当前应用都允许，且个人化组件在运行。上屏后 0.25 秒内没有按键才发出请求，期间按键即取消。
  • 个人化组件先从最近 5000 段上屏中找用户写过的接续（最多 3 个），再请主控续写（/v1/continue，k=8、6 个 token），首 token 是汉字且概率 ≥ 0.2 才采用，合计最多 5 个。
  • 发出后 1 秒内无答复则放弃；未激活时淡显 3 个，4 秒后收起；按 Tab 激活后可用数字、空格选择。

工具协议

工具在配件清单的 capabilities 中声明协议版本（1）、socket 路径、可报事项（reports[]：kind、title、默认 urgency）和动作（actions[]），并在自己的 Unix socket 上提供 MCP 子集。完整规格见 luoke-agent/docs/工具协议.md。目前没有已发布的配件在清单中声明 capabilities：邮件助手的实现默认关闭，agent 实际只有记忆一个来源。

传输

  • 每个请求一条连接：POST /mcp，请求体为一条 JSON-RPC 2.0 消息，上限 1 MB；MCP 协议版本 2026-07-28，在 params._meta 中携带。
  • 超时：连接 10 秒；读 outbox、列工具 10 秒；只读调用 30 秒；写调用 300 秒。socket 不存在视为工具未运行，不算错误。

何时说

  • 排序：urgency（urgent、normal、low）→ deadline → 首次出现时间。
  • 每类的方式（modes）：now、brief、window、off；未设置时 urgent 为 now，其余为 brief。
  • 急事：用户在 Mac 前（120 秒内有上报、未锁屏、屏幕未睡、空闲 < 180 秒）时立即通知，不受免打扰时段限制。
  • 简报：第一件待简报的事项（normal；只有 low 时距上一份 low 简报 ≥ 24 小时）出现后计时 60 分钟，到点后等用户在场且不在免打扰时段才发；每份含全部 normal，最多附 2 件 low；通知正文列前 3 个标题；上一份未打开窗口时新的一份静音。
  • 窗口：窗口打开时，现有事项都算看过，不再为它们发通知。
  • 少说：同一类连续 3 次没有回应，从 brief 降为 window，并给出一张"以后只放在窗口里"的卡片。
  • 清理：过期事项撤下；完成的卡片 30 分钟后撤下；完成或撤回超过 30 天的记录删除。

  • 写调用只在 POST /action（用户点按）时发出，并附 user-action；方案编号、链接、问题编号等写死的值只认核心保存的卡片声明，不采用界面送来的同名值。
  • 工具和记忆送来的文字一律按纯文本渲染；每张卡片带来源前缀，按钮只转给出这张卡片的来源。
  • socket 只靠文件权限（目录 700、文件 600）限定在当前账户内，不核对调用方身份。

已知限制

  • 没有对话，不使用模型；outbox 靠轮询，未实现订阅。
  • 写调用只看 tools/list 的 readOnlyHint，不对照清单里声明的 actions。
  • deadline 只影响排序，过期不会标记；off 与 window 效果相同。
  • 从不发送 outbox_ack state:"shown"，工具无法据此停止自己的通知。
  • 设置没有界面；卡片上用户改过的选项只存在壳里，壳重启后丢失；core.log 不轮转。
  • 简报通知的正文包含事项标题。
  • 核心只在启动时取一次主控的 luoke_mem 路径；主控升级后需重启核心才换用新的。

运行形态

入口行为
螺壳深度搜索.appbundle id ai.luoke.search，LSUIElement（不出现在程序坞）。主控在登录时带 --resident 拉起，打开即 serve；带 --resident 时向主控 PUT /accessory/resident，收到 SIGTERM 退出前 POST /accessory/exiting
luoke-search serve常驻服务：在 run/agent.sock 上提供 MCP，并跟着文件夹和照片图库更新索引；每 5 分钟补一次还在等的向量，每 2 分钟看一次设置、照片权限和文件夹能不能读；10 分钟没人搜就放掉内存里的向量。--socket 换 socket 路径，--no-watch 只开 socket
luoke-search index --job第一遍建索引（供主控的空闲任务调用）：同步设置里的文件夹和照片图库、读等着的、补向量；SIGTERM / SIGINT 时读完手上那个文件就停，退出码 0，下次接着读；标准错误只有计数
其他子命令同一个可执行文件 Contents/MacOS/luoke-search 也是命令行，见「接口」
  • 没有界面：用户在 agent 的对话里提问，agent 调 MCP 工具并画结果卡片；搜哪些文件夹、是否加入照片图库也由 agent 的卡片询问。
  • 读取和算向量分开：读取（取文字、OCR、抽帧、切声音）由本工具完成，读完即可按字词搜；向量找主控要，主控不在或忙时记为等向量，以后补。
  • 跟着文件夹：常驻服务启动时把文件夹走一遍（只看名字和时间，不读内容），移出不再搜的；之后用 FSEvents 盯着，变化停 0.75 秒后一起处理，只看变了的路径（新的、改过的、移动或改名的只改路径、删掉的、整个搬进来的文件夹）。新变的文件马上读，每次最多 50 个，排在第一遍的积压前面，读完补向量。设置改了就换成盯新的文件夹。
  • 第一遍兜底：常驻服务每 2 分钟检查一次，有等着读的且接着电源（或设置允许用电池）、不在低电量模式、不过热、主控说后台在跑时，读一段（最多 100 个）；文件一有变化就让路。
  • 长文件先读开头：超过 50 页的 PDF 第一遍只读前 30 页，超过 40 段的文档只读前 40 段，条目记为 partial，读到的部分照样能搜；所有文件都过一遍以后，再每次 30 页或 40 段往后补，每步读完就存，能停能续；文件改了从头读。盘拔了或内容被 iCloud 挪走时留到下次，不当成读不了。
  • 单个文件的看门狗（index、index --job、常驻服务都开着）：读一个文件时每秒看一次本进程内存和这个文件读了多久。内存超过上限（物理内存的一半，限在 4–8 GB）且至少一半是读这个文件时涨的，或读了 15 分钟（只算 Mac 醒着的时间），就把这个文件（连同修改时间和大小）和原因写进 run/stopped-file.json，以退出码 75 结束进程；下次起来先把它记为读不了，文件改过才重读。
  • 读到一半进程没了：每个条目记读的次数，两次都没读完就不再读（长文件的后续部分同样计数，已读的留着）。
  • 照片图库：常驻服务盯着图库的变更通知（变化攒 2 秒合一次），新拍的马上读。第一次要读时弹系统的询问框，问的时候文件夹照样在跟。
  • 线程：所有活在常驻服务自己的一条串行队列上；读文件（尤其 OCR）不在 Swift 并发的线程池里做，一个进程同时只做一张 OCR。
  • 签名：hardened runtime，权限只有 Apple Events（让 QuickTime Player 跳到某一刻）和照片图库。

不读什么

  • 不跟符号链接；不进包（含照片图库的包，图库经 PhotoKit 读）、隐藏文件夹、~/Library、*.noindex、开发用文件夹（node_modules、venv、site-packages、DerivedData、Pods 等）和用户跳过的文件夹。
  • 代码项目（含 .git、package.json、Package.swift、pyproject.toml、Cargo.toml、.xcodeproj 等的文件夹）里只读截图。
  • 只在 iCloud、没下载到本机的文件不读（读会触发下载）。
  • 像数据集的文件夹：同一个文件夹里同一类媒体（图片、视频、录音）≥ 300 个、其中 ≥ 70% 是机器起的名字（纯数字、十六进制串和 UUID、frame_0042、clip-000123 这类数据集词加数字），这一类不读，文档照读。相机和系统起的名字（IMG_、DSC、PXL_、截屏等）、名字里带日期的、其他词加数字的不算；图片再抽 10 张看 EXIF，一半以上写了相机厂家或型号的不跳。用户直接选的文件夹（含套在另一个选中文件夹里的）不算。status 和 search_status 列出这些文件夹。
  • 凭证文件不读：按扩展名（pem、p12、kdbx、key、ovpn 等）、名字开头（id_rsa、.env、.netrc 等）、名字里的词（password、credentials、secret、api key、recovery codes、seed phrase 等）、中日韩片段（密码、口令、密钥、私钥、助记词、恢复码等）和密码管理器的导出（logins.csv、bitwarden / lastpass 导出、keepass）。单独的 key、token 不算。
  • 拔掉的盘、macOS 不让读的根文件夹记为读不了，其中已有的条目保留。

怎么搜

  • 按字词：SQLite FTS5 两张表，fts（unicode61 + Porter 词干）和 fts_tri（trigram，给中文、日文等不用空格的文字）。查询中的中日文用系统分词（NLTokenizer）切词，去掉停用词和相对时间词（"上个月""去年"等，交给 agent 换成 since / until）；分词器拆成单字的相邻字连起来再试（可选词：找到每个加 0.1、最多 0.3，找不到不扣，不能单独让条目入围）；三个字以上走 trigram，两个字用 LIKE；英文找不到原词时按前缀匹配。
  • 类型词：查询中的"截图""照片""录音""视频""PDF""文档"等不当关键词，给对应类型加分（不是筛选），这类条目按意思 z ≥ 1 即入围；"照片"同时指文件夹里的图片和图库的照片。只有类型词、按意思也没找到时，列出该类型最新的条目。
  • 按意思：查询向量以 user-waiting 向主控要（模型在加载时最多等两次）。全部向量以 fp16 存在索引里，搜索时整块读进内存，每 1024 行转 fp32 用 vDSP 求余弦。每个条目取最好的一段。
  • 混合打分（默认做法 A）：余弦先换成 z 分：满 20 行的模态（文字、图片、声音）按自己的均值居中，不满的按全体均值；离散度全体合着算，每行跟其余各行比（留一法），并向典型值 0.03 收缩。条目入围条件：z ≥ 2（类型词对上时 ≥ 1），或含必需的查询词至少一半。分数 = z + 2 ×（命中词比例）1.5 + 0.5 × 名字中的命中比例 + 0.3 × 名次项 + 类型词加 1。查询的词都含数字（编号、单号）时按精确查找：字词权重加倍、z 减半。
  • 其他打分做法只在 eval --scoring 里用于对比：b（每个模态只和自己比）、c<k>（模态的均值和方差按 k 行的分量往全体拉）、d（各自均值、离散度合着算）。
  • 结果：分数不到第一名一半的标 strong: false（卡片上标"可能相关"）；原文件已不在的不列出。结果指向含查询词最多的一段（名字和内容都对得上时指向内容）；按意思入围的指向意思最好的那段。表格命中时片段是含查询词的一两行，每格前写列名。片段和标题送出前遮掉凭证（密码、验证码、密钥、卡号、证件号换成〔密码〕这样，规则同记忆的凭证遮蔽）；索引里保留原文。
  • 拒答门槛未开：没有结果时 confident 为 false，有结果时为 null（"有结果但说不准"）。候选门槛（字词全中，或第一条的余弦过它那个模态的门槛：文字 0.70 / 图片 0.66 / 声音 0.70）只在 eval --refusal 里量，是否开启待定；开启后没过门槛的结果照给、标 confident: false。

依赖主控

  • 任务：客户端请求的任务名为 luoke-search.embed（配件清单同名；开发时 LUOKE_SEARCH_EMBED_TASK 可换）。主控主线配方中该任务仍叫 digup.embed 且未分配到任何档，所以对当前主控，GET /tasks 里没有 luoke-search.embed，深度搜索判为"这版主控还不认识深度搜索"，只按字词搜。
  • 接口：GET /tasks 读状态和参数（batch、max_chars、max_total_chars、vector_space，以及 image_batch、image_budgets、audio_batch、max_image_bytes、max_audio_bytes、max_audio_secs），X-Luoke-Tasks-Version 变了就重读；POST /tasks/<任务>/v1/embed 送 texts 或 inputs（图片、声音的字节，不送路径）。请求头 X-Luoke-Accessory: luoke-search/0.1.0、X-Luoke-Priority，需要时 X-Luoke-Allow-Battery。要求 768 维，收到后再做 L2 归一化。
  • 提示词：查询 task: search result | query: …；文档 title: … | text: …（标题用文件名，PDF 用它自己的标题）。
  • 图片和声音：索引里不存像素和声音；主控的参数表明收某一种时，从文件重新做出同样的帧和窗口再送。预算：照片和图片 JPEG ≤ 1024 px、140；截图 PNG ≤ 1536 px、280；扫描页 PNG 1400 px、280；视频帧 JPEG ≤ 1024 px、70；声音 30 秒 WAV。一个一个做、攒够一批就发；这一档不收的预算照旧等；暂时失败的试 3 次，主控说读不了的那条不再要向量。补向量时重做图片和声音这一步不在看门狗下。
  • 主控不在或忙：照常读取、按字词搜，答复带 partial_reason（主控没在运行、不认识深度搜索、这台 Mac 不提供、还有多少段等向量等），不退回任何自带模型。补向量时 power_cooldown、lane_busy 这类短歇原地等完；其他拒绝停下、下次再补（index --wait 时按 retry_after_ms 等，连续没进展才翻倍，最多 300 秒）。vector_space 变了只重算向量，不重读文件；空间不一致时这次只按字词搜。
  • 开发不碰正在用的主控：只有默认数据目录 ~/.luoke-search 才回退到已安装主控的 socket；带 --index 或 LUOKE_SEARCH_HOME 的运行只认 LUOKE_HUB_SOCKET，没设就只按字词搜。

故障

  • 主控不在、忙或任务不可用：照常读文件、按字词搜，向量以后补；答复带 partial 和一句说明。
  • 还在建索引或长文件没读完时答复带 partial（"还有 N 个文件没读""还有 N 个长文件没读完"）；图片、视频、录音在等主控时说明暂时只能按名字和里面的字找到。
  • 文件读不了（加密 PDF、打不开的视频格式、只在 iCloud 的图库视频）记为 failed，不影响其他文件；文件消失后结果不再列出，search_open 答 stale。
  • SIGTERM：手上那个文件读完就停，删掉自己的 socket；剩下的下次接着读。
  • 单个文件读得过久或内存失控：看门狗记下该文件、以退出码 75 退出，由主控重新拉起；该文件记为读不了，改过才重读。

主控任务接口

主控在 Unix socket 上提供的 HTTP/1.1 接口，供配件调用。每次请求一条连接。

连接

  • socket：~/Library/Application Support/luoke-core/run/hub.sock（目录 0700，文件 0600）。配件依次查找：显式路径 → 环境变量 LUOKE_HUB_SOCKET → 默认位置。
  • 身份：请求头 X-Luoke-Accessory: <配件>/<版本>。版本须在配方 verified 中，或本机放行，或是本机 verified-history.json 中有记录的已安装版本（换回的上一版，只能用记录中的任务）；带任务名的请求还要求任务存在且属于该配件。
  • 响应头：X-Luoke-Contract: 1、X-Luoke-Tasks-Version（配方、档、模型分配、引擎版本、任务参数的摘要，变化即应重读 /tasks）。
  • 请求体上限 32 MB。

错误

错误体为 {"code", "message", "retry_after", …}；有 retry_after 时同时给 Retry-After 头。

HTTPcode含义
400invalid_request请求格式或参数不合法
403unknown_accessory配件或版本未通过验证，或任务不属于该配件
403forbidden主控本体专用的路由，对端不是本体（或允许的命令行）
404task_unavailable、unsupported任务不存在；本档不支持该任务；换回的上一版调用其记录外的任务
413input_too_long超过任务的 max_chars
503busy暂时不能接纳，附 reason（见主控 · 后台接纳）
paused全机后台暂停或本档放不下
not_ready模型正在加载或工作进程按需重起（retry_after 2）；内存不够或内存压力 critical 后暂不启动工作进程（retry_after 30）
needs_user用户在等但内存放不下，附 occupants（占用内存的进程）
engine_failed引擎或工作进程出错

流式生成过程中的错误以 event: luoke.error 事件给出，另有 interrupted（后台请求被用户请求打断）。

任务

GET /tasks

返回 {contract, hub_version, tier, tasks_version, background: {state, reasons}, tasks: {<名>: {kind, status, reason, progress, slow, combo, params, vector_space?}}, luoke_mem?: {path, version}}。只列出请求方自己的任务；luoke_mem 给出主控内置的记忆库路径。

生成 POST /tasks/<task>/v1/chat/completions

  • 任务 kind 为 generate。请求为 OpenAI 格式的 messages，必须 stream: true，带 luoke_items（本批条目数，≤ batch）；response_format 可用 json_schema 或 json_object。
  • 请求头 X-Luoke-Priority 必填（user-waiting 或 background）；X-Luoke-Allow-Battery: 1 可选。
  • 主控覆盖：max_tokens = item_tokens × luoke_items + fixed_tokens；采样参数取配方；中和消息中的模型特殊 token；答复中的 model 改写为组合名。
  • SSE 流中另有 event: luoke.progress（queued、loading、running）。

打分 POST /tasks/<task>/v1/score

kind score。请求 {context, candidates}（候选 ≤ batch，默认 16；前文 ≤ max_chars，默认 2000）；答复 {logprobs, model, cache_hit, ms}。超时 10 秒。

续写 POST /tasks/<task>/v1/continue

kind predict。请求 {context, k?, max_tokens?, stop?}；答复 {branches: [{tokens: [{text, logprob}], finish}], model, cache_hit, ms}。旧接口 /v1/predict 仍保留。

嵌入 POST /tasks/<task>/v1/embed

kind embed。请求 {texts: [...]}（任务参数允许时可用多模态 inputs）；答复 {vectors, dims, model, vector_space, ms}。默认每批 32 条、单条 32000 字、合计 320000 字。后台请求走专用模型通道，被挡回时返回 lane_busy 并附 retry_after_ms。

预热 POST /warmup

请求 {task, lease_id?}；答复 {accepted, lease_id, expires_in: 600}，或 {accepted: false, code}（task_unavailable、unsupported、deferred）。新的预热算作交互，续期不算。打分、联想、嵌入任务的预热会启动工作进程；内存不够时照样答应，真正请求时答 not_ready。

提示词约定

  • 提示词写在调用方配件里，随请求发给主控；主控不保存、不记录请求文字。
  • 输出一律用 JSON schema 约束；配件负责解析和校验，失败时有明确的退路（重问一次、判为保留、跳过）。
  • 输出上限由主控按 item_tokens × 条目数 + fixed_tokens 定，调用方给的 max_tokens 不用。
  • 邮件、网页、打的字等输入一律声明为数据，其中给 AI 的指令不执行。
  • 结果的数量、依据和把握程度由代码判定，模型只负责提名；例外是订阅阅读的分数由模型给，≥ 2 才进精选候选。

评测

  • 评测集和硬性条目写在主控的 tools/release_evals.json，评测结果写入配方的 evidence，并决定各档开关。起草回复、订阅阅读、精选挑选没有评测，各档一直沿用上一版的"开"。
  • 分拣的硬性条目：正常邮件零误报，可疑邮件最多漏 1 封。
  • 往来邮件：已了结的不能报为"等你"，"等你"的不能漏，都一次不能错。模型答"轮到谁"（user_turn / other_turn / done），由代码映射为等你 / 在等对方 / 已了结。
  • 话题归纳：只写品牌名或来源名即为失败；另记是否有具体对象。

提示词

每个生成任务的提示词要点：送进去什么、要求输出什么、代码怎么校验、失败时怎么退。只做摘要，原文在各配件仓库。任务名、种类和各档开关见「任务与提示词」。

共同做法

  • 提示词、输出 schema 和校验都在调用方配件里；主控只做通用的生成：不思考（enable_thinking 关），把 response_format 的 JSON schema 交给引擎约束，消息里的特殊 token 先中和。
  • 输出上限由主控定：item_tokens × 条目数 + fixed_tokens；调用方给的 max_tokens 不用。输入超过任务的 max_chars 答 input_too_long，条目数超过 batch 拒绝；调用方事先按上限二分截短或减少条目。
  • 输入里的邮件、订阅、打的字一律声明为数据，其中给 AI 的话不执行。
  • 结果多少、能不能生效、把握几档由代码和记忆的表决定；模型只负责提名和分类。
  • 两个客户端都不看 finish_reason：输出被截断时按"无法解析"处理。

出版流程

  1. 读取钉住的各组件提交，打包配件 .app。
  2. 按配方在各档评测每个任务，每一格（任务 × 档）当天只评一遍；已有且输入未变的证据复用。
  3. 评测看门狗：某档某任务 10 分钟没有进展（生成任务看实验室主控日志里有没有成功的请求，其他任务看评测程序的输出是否增长），即停掉评测程序，这一格记为没过（engine_refused_memory 或 stalled），接着评其余各格。
  4. 按支持台账决定各档开关：上一版开着的，失败一遍即关；关着的（上一版关、新任务、评测表 hold 的）当天过了也照"关"发布；这一版没评的档沿用上一版。生成配方和差异报告；仍开着的组合总分比上次低出容差，或主要任务一档都没开时停止。
  5. 签名、公证、生成 DMG 和发布清单，上传。目标是当天 24:00（JST）前发出，不等复测。
  6. 发布后复测：关着、当天过了的格子再补跑到 3 遍（hold 的不复测，失败一遍即停），结果只写回这一版的证据和台账，不改已发布版本的开关。下一版中，上一版补满 3 遍都过、这一版也过（或没评）的格子开启。

每一步记录在 steps.json 中，失败后可以从中断处继续；复测中途停下，下次接着补。

换装与回滚

  • 用户：主控菜单「检查更新…」下载并核对新版后原地升级，或手动打开新版安装器；数据和模型保留；旧版保存在 previous.noindex，可回到上一版。单个配件可经「配件回到上一版…」换回旧版，主控按那一版当时的验证接受它。
  • 开发：本机版用同样的安装器升级；配件的新版本可经"本机放行"在内部版或本机版主控上先行使用。

设计原则

  • 合理默认，按反馈逼近：不要求用户事先设定规则或逐条审阅；用户的确认、否定和撤销就是调整的依据。
  • 测试版不过度保守：能撤回的能力默认开启，配上提示和撤销，通过真实使用检验。
  • 本地优势不打折：在本机内部充分使用数据，体验才能弥补本地模型和算力的差距。
  • 产出要像用心的助理：理解要说清领域和具体对象，不照搬标题或品牌名。
